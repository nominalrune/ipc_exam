# 持ちネタ事例 2本

> 方針: AWS上のシステムを題材にした架空の事例を2本持ち、問題文に合わせて**焦点だけ変える**。各事例に「予算制約による妥協点」を置き、監査人が指摘・評価できる材料にする。
> 立場はどちらも **「A社 内部監査室のシステム監査担当（私）」** で統一する（独立性を説明しやすい）。

| | 事例A: 会員EC基盤 | 事例B: データ活用・新規開発 |
|---|---|---|
| 一言でいうと | 止まると売上が止まる、外部サービスに頼る基幹系 | 新しい技術・新しい作り方で、組織横断のデータを扱う |
| 妥協点 | DBシングルAZ＋バックアップで補完 | 少人数チームのため開発者が本番デプロイ可能（パイプラインの承認で補完） |
| 得意なテーマ | 可用性・障害管理態勢・IT-BCP・外部委託／外部サービス・運用・個人情報 | データ利活用・新技術／新手法・アジャイル・IT投資ガバナンス・変更管理・内部不正 |

---

## 事例A: 生活雑貨EC「Bストア」の会員・受注システム

### A-1. 組織（アの第1段落）
- A社: 生活雑貨の製造小売。従業員約800名、店舗60、売上約300億円のうち**EC比率が35%**で年々増加
- 中期経営計画で「EC売上比率50%」を掲げ、ECの安定稼働が経営課題になっている
- 情報システム部（25名）がECを所管。開発・運用の一部は**SIer の C社（運用保守委託）**に委託
- 私は内部監査室（5名、うちシステム監査担当2名）に所属。社長直轄で、情報システム部からは独立している

### A-2. システム（アの第2段落）
- Bシステム: 会員管理（会員約120万人、個人情報・購買履歴）、受注、決済連携、在庫照会
- 2024年にオンプレミスから **AWS へ移行**。構成: CloudFront → ALB → ECS（Fargate、2AZに分散）→ RDS for PostgreSQL
- 決済は外部の決済代行サービス、配送は物流会社のAPI、問合せ対応はSaaSを利用（**外部接続先が多い**）
- 24時間365日稼働。目標: 稼働率99.9%、RTO 4時間、RPO 15分

### A-3. 特徴（アの第3段落に2〜3点選んで書く）
1. **【妥協点】予算制約により RDS はシングルAZ構成**。マルチAZにすると DB 費用がほぼ倍になるため、経営会議で「自動バックアップ（ポイントインタイムリカバリ）＋日次スナップショットの別リージョン複製」で補うことを承認した。AZ障害時は**スナップショットから復元（想定2〜3時間）**する手順で RTO 4時間を満たす設計
2. **運用の大部分を C社に委託**。インフラ監視・一次対応・パッチ適用は C社、変更承認と障害時の判断は A社情報システム部。AWSとの間は**責任共有モデル**による責任分界がある
3. **外部サービスへの依存**: 決済代行・物流API・問合せSaaS。いずれかが止まると受注が止まる／遅れる
4. 繁忙期（年末・セール）にアクセスが平常時の5倍。ECSはオートスケーリングするが、DBは固定サイズ

### A-4. 監査の契機（アの第4段落の候補）
- 前年のセール時に決済代行の障害で**3時間受注停止**、売上約8,000万円の機会損失 → 取締役会が「障害管理態勢の監査」を指示
- 個人情報保護法の改正対応／漏えい時の報告義務
- クラウド移行から2年経ち、委託先モニタリングの実効性を確認する時期

### A-5. 監査人が見るポイント（イ・ウの材料）

| 論点 | リスク | 期待されるコントロール | 監査証拠 |
|---|---|---|---|
| 妥協点（シングルAZ） | AZ障害時にRTO 4時間を超える／PITRで復旧できない | 復旧手順書があり、**定期的に復旧テストを実施**し所要時間を記録。リスク受容が経営の承認を得て、定期的に見直されている | 経営会議議事録（リスク受容の承認）、復旧手順書、**復旧テスト記録（所要時間）**、AWS Backup／RDS スナップショットのジョブ履歴、別リージョン複製の設定（AWS Config） |
| 外部委託（C社） | C社の監視漏れ・対応遅延、権限の過大付与 | SLA・報告義務を契約で定め、月次報告で A社が評価。C社の IAM 権限が最小限で棚卸されている | 委託契約書・SLA、月次運用報告書、定例会議事録、IAM ロール一覧、CloudTrail（C社ロールの操作）、権限棚卸記録 |
| 外部サービス | 決済代行等の障害で受注停止／障害の検知が遅れる | 外部サービスの稼働をA社側でも監視。障害時の代替手段（後払い・受付停止画面）と連絡体制を定めている | CloudWatch の外形監視・アラーム設定、障害対応手順書、外部サービス事業者の SLA、過去障害の障害報告書 |
| 責任分界（AWS） | AWS側の統制を確認せず「クラウドだから安全」と思い込む | AWS の SOC 2 報告書を入手・評価している。利用者側責任（設定・ID管理・データ）を自社で管理 | AWS Artifact から入手した SOC 2 報告書と評価記録、責任分担表 |
| 繁忙期の性能 | DBが固定サイズのため繁忙期に性能劣化 | 性能監視のしきい値と、繁忙期前のキャパシティ計画 | CloudWatch のメトリクス・アラーム履歴、キャパシティ計画書 |
| 個人情報 | 会員情報の漏えい | 暗号化、アクセス権の最小化、アクセスログの定期レビュー | RDS 暗号化設定（Config）、IAM ポリシー、ログレビュー記録 |

### A-6. 焦点の切り替え例
- **障害管理態勢**（R4問2型）→ 外部サービス障害・C社との連携・障害報告→再発防止の PDCA
- **IT-BCP**（R7問2型）→ シングルAZの妥協点を中心に、大規模災害（リージョン障害）まで広げる。**結果事象**（DBが使えない、拠点に入れない、C社要員が出社できない）からリスクを洗う
- **外部サービスを活用した運用プロセス**（R6問2型）→ C社＋決済代行＋AWS の責任分界と、A社のモニタリング
- **サイバーセキュリティ管理態勢**（R5問2型）→ 会員個人情報を守る態勢。GuardDuty の検出から CSIRT 対応までの PDCA

## 事例B: 製造業D社の「需要予測・データ活用基盤」をアジャイルで構築

> 事例Aと同じA社にするか別会社にするかは自由。**別会社（D社）にしておく**と、両方を同じ立場で書いても混乱しない。

### B-1. 組織
- D社: 業務用厨房機器メーカー。従業員約1,500名、国内工場3、海外販売拠点2
- 経営課題: 部品の欠品と過剰在庫。**DX推進室**（2023年設置、8名）が全社のデータ活用を推進
- 私は内部監査室のシステム監査担当

### B-2. システム
- Eシステム（データ活用基盤）: 基幹システム（オンプレミスのERP）、販売管理、工場の生産管理、**海外販売拠点の受注データ**を AWS に集約し、需要予測と在庫の可視化を行う
- 構成: 各システム → 日次バッチで S3（データレイク）へ → Glue で加工 → Athena で集計 → QuickSight のダッシュボード。需要予測は SageMaker の機械学習モデル
- 利用者: 経営層、営業企画、工場の生産計画担当（約200名）
- 開発は**DX推進室の内製チーム（5名）が2週間スプリントのアジャイル（スクラム）**で実施。D社にとって**初めてのアジャイル開発・初めての機械学習**
- 投資額: 初期1.2億円、年間運用3,000万円。経営会議で「欠品率を半減、在庫を20%削減」を効果目標として承認

### B-3. 特徴
1. **【妥協点】少人数のため、開発者が本番環境へのデプロイ権限を持つ**（職務分離が不十分）。代わりに、CodePipeline に**プロダクトオーナーの承認ステージ**を必須とし、デプロイは全て CloudTrail に記録、**月次で内部統制担当が操作ログをレビューする**ことで補完
2. **複数システムからデータを集めるためデータ品質が揃わない**（品目コードの不一致、海外拠点の入力遅延）
3. **新しい手法・技術**: アジャイルで要件が変わり続ける。機械学習モデルの予測根拠が説明しにくい
4. **海外拠点のデータ**を扱うため、各国の個人情報・データ移転規制への配慮が必要（取引先担当者の情報を含む）
5. IT投資の効果が出るまで時間がかかり、**投資判断の見直しの仕組み**が必要

### B-4. 監査の契機
- 経営会議で「Eシステムの予測値をもとに発注を自動化する」案が出た → 自動化の前に、データの信頼性と開発・運用の統制を確かめたい
- 投資から1年経過し、効果目標の達成状況を評価する時期
- 監査等委員会からの要請

### B-5. 監査人が見るポイント

| 論点 | リスク | 期待されるコントロール | 監査証拠 |
|---|---|---|---|
| 妥協点（職務分離） | 開発者が未承認の変更を本番に反映／不正な変更 | パイプラインの承認ステージを迂回できない設定。緊急時の直接操作は事後承認。月次ログレビュー | CodePipeline の承認履歴、IAM ポリシー（承認なしデプロイの禁止）、CloudTrail の本番操作ログと**承認記録の突合**、月次レビュー記録 |
| データ品質 | 誤ったデータで予測→誤発注 | データの受入チェック（件数・コード整合）、品質指標の監視、データオーナーの決定 | Glue ジョブのチェック結果ログ、データ品質レポート、データ管理規程・データオーナー一覧 |
| アジャイル | 要件変更が統制されず、重要な機能（権限、監査ログ）が後回し | プロダクトバックログに非機能要件を含め、スプリントレビューで利用部門が受入れを判断。完成の定義（DoD）にセキュリティ確認を含む | プロダクトバックログ、スプリントレビュー議事録、DoD、受入れ記録 |
| 機械学習 | 予測精度の劣化に気付かない／判断根拠が説明できない | 精度指標を定期モニタリングし、しきい値を下回ったら再学習。モデルの変更を変更管理に含める | 精度モニタリング記録、モデルのバージョン管理記録、再学習の承認記録 |
| IT投資ガバナンス | 効果が出ないまま投資が続く | 投資時に効果指標を定め、定期的に経営会議で評価・継続判断 | 投資稟議書、効果測定報告、経営会議議事録、Cost Explorer の実績 |
| 海外データ | 各国規制違反 | 取り扱うデータの棚卸しと、法務部による規制確認 | データ棚卸表、法務部の確認記録、S3 のリージョン設定 |
| アクセス権 | 200名に過大な閲覧権限 | 役割ごとのダッシュボード権限、定期棚卸 | QuickSight の権限一覧、権限棚卸記録 |

### B-6. 焦点の切り替え例
- **データ利活用基盤の構築**（R5問1型）→ 構築理由（欠品・過剰在庫）とデータ品質のリスク。**講評でデータ品質のリスクに触れた解答が少なかった**ので、ここを厚く
- **新技術・新手法の特有リスク**（R7問1型）→ アジャイル＋機械学習。「リスク許容範囲内まで低減できるか」の評価
- **IT投資のガバナンス**（R6問1型）→ **組織全体の**投資管理の仕組み（投資委員会、評価基準）を語る。Eシステムは「その仕組みが機能しているかを確かめる一例」に留める
- **アジャイル開発の監査** → 監査人がスプリントレビューに参加する、継続的な監査
- **内部不正**→ 職務分離の妥協点を中心に

## 2本の使い分け早見表

| 問題文のキーワード | 使う事例 | 中心に据える論点 |
|---|---|---|
| 障害、可用性、事業継続、BCP、災害 | A | シングルAZの妥協点、外部サービス |
| 委託、外部サービス、クラウド、SaaS | A | C社・AWSの責任分界、委託先モニタリング |
| 個人情報、サイバーセキュリティ | A | 会員情報、検知から対応までの態勢 |
| データ、データ利活用、AI | B | データ品質、予測モデル |
| アジャイル、新技術、DX | B | 新手法の特有リスク、職務分離の妥協点 |
| IT投資、ITガバナンス、経営 | B | 投資効果の評価の仕組み（組織全体） |
| 変更管理、内部不正、アクセス管理 | B（Aでも可） | 本番デプロイ権限の妥協点 |
| 監査計画、監査手続の制約 | どちらでも | 監査資源の制約→代替手続（例: 全件確認の代わりにConfigルールの評価結果を利用） |
