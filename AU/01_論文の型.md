## 1. 時間配分（120分）

キーボード入力なので手書きより速い。その分を**設計と見直し**に回す。

| 時間 | やること |
|---|---|
| 0〜15分 | 2問を読んで選択（5分）→ メモ用紙に**骨子**を書く（10分）。設問ア・イ・ウの見出しと、イの項目・ウの手続を対応付けた表まで作る |
| 15〜35分 | 設問ア（20分） |
| 35〜75分 | 設問イ（40分） |
| 75〜105分 | 設問ウ（30分） |
| 105〜120分 | 見直し（15分）。問題文のキーワードが見出しに入っているか、イとウの対応、字数の下限 |

**下限割れは致命傷**（イ800字・ウ600字未満は設問に答えていないとみなされ、大きく評価を落とすと考えておく）。時間が押したら、ウの最後の手続を1つ減らしてでも下限を守る。

### 選択の基準（Keiの持ちネタ前提）

1. 持ちネタ事例A・Bのどちらかがそのまま載るか（問題文の「対象」と事例の対象が一致するか）
2. 問題文の要求が **「リスク→手続」型** か **「着眼点→証拠」型** か（後者は「確かめる内容」を書く必要があり、書き分けを練習した方を選ぶ）
3. 「態勢」「組織全体」「経営」を問う問題は、個別システムの話に寄せると減点される（R4問2・R5問2・R6問1の講評）。事例の会社全体の仕組みまで語れる方を選ぶ

## 2. 章立て（見出しの付け方）

見出しは**問題文の言葉をそのまま使う**。採点者は見出しで設問への対応を確認する。

```
第1章 （設問アの問いの言葉）
 1.1 対象組織と業務の概要
 1.2 対象システム（または態勢）の概要
 1.3 （問題文が求める「特徴」「理由」「役割・責任」など）
第2章 （設問イの問いの言葉）
 2.1 （リスク／着眼点①）
 2.2 （リスク／着眼点②）
 2.3 （リスク／着眼点③）
第3章 （設問ウの問いの言葉）
 3.1 （①に対応する監査手続）
 3.2 （②に対応する監査手続）
 3.3 （③に対応する監査手続）
```

- **イの項目数＝ウの項目数**にして番号で対応させる（2.1↔3.1）。イに書いてウで扱わないものを作らない
- 項目は2〜3個。4個以上にすると1個あたりが浅くなる
- 「以上」は不要。最後の段落を書き切って終える

## 3. 設問ごとの書き方

### 設問ア（650〜750字）: 概要と特徴

段落構成（5段落）:

1. **組織**: 業種・規模・事業の状況（2〜3文）
2. **対象**: システム（または態勢）の目的・構成・利用者（3〜4文）。AWS構成はここで1〜2文だけ
3. **特徴**: 問題文が求める特徴を**2〜3点、番号付き**で。イのリスクの「種」をここに埋める（例: 予算制約によるシングルAZ構成）
4. **監査の位置付け**: 私の立場と、なぜ今この監査をするのか（経営からの依頼、前年度の指摘、制度変更など）
5. （字数調整用）関係部門と役割分担

> アで「特徴」を書いておくと、イで「この特徴から○○のリスクがある」とつなげられる。**アはイ・ウの伏線**。

### 設問イ（1,200〜1,400字）: リスク／着眼点

各項目を次の4点セットで書く（1項目 400〜450字）:

1. **何が起きると困るか**（リスク）または **何を確かめるか**（着眼点）を1文で言い切る
2. **なぜそう考えたか**（アの特徴とのつながり）
3. **影響**（業務・経営への影響。金額や時間で書けると強い）
4. **期待されるコントロール**（本来どうなっているべきか）

> 「期待されるコントロール」まで書くと、ウで「それが整備・運用されているかを確かめる」とすっきりつながる。

### 設問ウ（900〜1,000字）: 監査手続・監査証拠

各項目を次の型で書く（1項目 300〜330字）:

```
（イの①）に対しては、次の監査手続を実施する。
・（何の文書／ログ／記録）を入手し、（何と何を）照合して、（何が）（どうなっていること）を確かめる。
・（担当者）にインタビューを行い、（何）を確認する。ただしインタビューだけでは証拠力が弱いため、（記録）と突き合わせる。
・（期間）の（記録）から（件数／抽出方法）を抽出し、（承認／実施）の有無を確かめる。
```

**手続の6要素**（全部そろうと「具体的」と評価される）:
- 何を（監査証拠: 文書名・ログ名・記録名）
- どうやって（閲覧・突合・観察・再実施・インタビュー）
- どの範囲で（期間・件数・抽出方法）
- 誰に（インタビュー相手）
- 何を確かめる（判断基準: 承認がある、期限内、一致する）
- 不備ならどう判断する（任意。余裕があれば1文）

**「確かめる内容」を問われたら手続を書かない**（R4問2の講評）。その場合は「〜が〜となっていること」「〜が〜以内であること」という**状態の記述**で書く。

## 4. 書き出しの定型（コピペして埋める）

### 設問ア
- 「私が所属するA社は、〜を営む従業員〇名の〜である。私はA社の内部監査室に所属し、システム監査を担当している。」
- 「本稿では、A社が〜年に構築した〜システム（以下、Bシステムという）について述べる。」
- 「Bシステムの特徴は、次の〇点である。」
- 「A社では〜を契機として、Bシステムを対象とするシステム監査を実施することになった。」

### 設問イ
- 「Bシステムの特徴を踏まえ、私は次の〇点をリスクとして想定した。」
- 「〜という特徴があるため、〜が発生するリスクがある。」
- 「このリスクが顕在化すると、〜により〜という影響が生じる。」
- 「したがって、〜というコントロールが整備・運用されている必要がある。」
- 「私は、〜を監査の着眼点とした。その理由は、〜だからである。」

### 設問ウ
- 「設問イで述べたリスクに対して、私は次の監査手続を設定した。」
- 「〜を入手・閲覧し、〜が〜であることを確かめる。」
- 「〜と〜を突合し、両者が一致していることを確かめる。」
- 「〜の期間から〜件をサンプリングし、〜の承認記録があることを確かめる。」
- 「〜は〜のため、インタビューに加えて〜の記録を入手し、裏付けを取る。」

## 5. 監査人視点の言い回し（言い換え表）

| ×（当事者・技術者の書き方） | ○（監査人の書き方） |
|---|---|
| マルチAZ化した | マルチAZ構成が**設計書どおり設定されていることを**、設定画面の写し（AWS Config の記録）で**確かめる** |
| 〜すべきである／〜を導入した | 〜が**整備されているか**、〜が**運用されているか**を確かめる |
| 担当者に確認する | 担当者に**インタビューし**、その内容を〜の**記録と照合する** |
| ログを見る | 〜期間の CloudTrail ログを**入手し**、〜の操作が承認記録と**一致することを確かめる** |
| 問題がないか確認する | 〜が〜**以内であること**（判断基準を明示）を確かめる |
| 対策を実施した（自分が） | 〜部が対策を実施している。監査人として**その有効性を評価する** |
| 体制 | 態勢（体制＋ルール＋運用＋モニタリング＋改善の仕組み全体） |

**経営判断（妥協点）の扱い方**: 「マルチAZにすべきだった」のように案の良し悪しを裁かない。確かめるのは **①代替案を比較した記録 ②残るリスクを理解したうえでの経営承認 ③前提が変わったら見直す仕組み** の3点。定型文: 「経営の判断を尊重したうえで、その判断のプロセスと前提が維持されているかを確かめる。」

**禁止事項**:
- 自分が対策を作る・直す立場で書く（監査人は独立した立場で確かめる）
- 「適切に」「十分に」で終わる（何をもって適切かを書く）
- 一般論だけで終わる（必ずアの事例固有の事情につなげる）

## 6. 監査用語ミニ辞典（論文で使う）

| 用語 | 意味・使いどころ |
|---|---|
| 予備調査 | 本調査の前に、対象の概要・リスクを把握する段階。アの「監査の位置付け」やイの理由で使う |
| 本調査 | 監査手続を実施して監査証拠を入手する段階。ウはこれ |
| 監査の着眼点 | 何を確かめるかの視点。「〜が〜されているか」の形 |
| 監査手続 | 監査証拠を入手するための具体的な方法 |
| 監査証拠 | 監査意見の根拠となる記録・文書・ログ |
| 整備状況／運用状況 | ルールや仕組みがあるか／実際にそのとおり動いているか。ウでは両方を確かめる |
| 準拠性監査／妥当性監査 | 規程どおりか／規程そのものが適切か |
| サンプリング | 母集団から抽出して確かめる。期間・件数・抽出方法を書く |
| 監査リスク | 誤った監査意見を出すリスク。R4問1で「代替手続」とセットで出題 |
| 責任分界点 | 委託元と委託先（クラウド事業者）の責任の境目。AWSの責任共有モデルで説明できる |
| 監査調書 | 監査手続の結果と証拠を記録したもの |
| フォローアップ | 改善提案のその後の実施状況を確かめること |

## 7. AWSを「監査証拠」として使う対応表

| 確かめたいこと | 監査証拠（AWS） | 監査証拠（AWS以外） |
|---|---|---|
| 誰が何をしたか | CloudTrail の管理イベントログ | 作業申請書・作業記録 |
| 設定が基準どおりか・変わっていないか | AWS Config の設定履歴・ルール評価結果 | 設計書・パラメータシート |
| 障害・性能の検知 | CloudWatch のアラーム設定と通知履歴、CloudWatch Logs | 障害報告書・障害管理台帳 |
| 権限が最小限か | IAM のポリシー・ロール一覧、IAM Access Analyzer の結果、認証情報レポート | 権限申請書・棚卸記録 |
| 脅威の検知と対応 | GuardDuty の検出結果、Security Hub のスコア | インシデント対応記録 |
| バックアップと復旧 | AWS Backup のジョブ履歴、RDS スナップショット一覧、**復旧テストの記録** | BCP・復旧手順書・訓練報告書 |
| 可用性構成 | RDS／EC2 のマルチAZ設定、ELB の構成 | 可用性設計書・SLA |
| 責任分界 | AWS の責任共有モデル、**AWS Artifact の SOC 2 報告書** | 委託契約書・SLA・委託先の報告書 |
| コスト・投資 | Cost Explorer、予算アラート | 投資計画書・稟議・効果測定報告 |
| 変更管理 | CodePipeline の承認ステージ履歴、Git のプルリクエスト承認記録 | 変更申請書・リリース判定記録 |

> **使い方の原則**: AWSのサービス名は「証拠の出どころ」としてウで1手続に1つまで。アでは構成を1〜2文。サービスの機能説明を書き始めたら技術論文になって減点される。

## 8. 採点講評から分かる「落ちる論文」チェックリスト

見直しの15分でこれを確認する。

- [ ] 問題文が「態勢」と言っているのに「体制」や個別システムの話をしていないか（R4問2、R5問2）
- [ ] 問題文が「組織全体」を問うのに、個別プロジェクトの話をしていないか（R6問1）
- [ ] 「確かめる内容」を問われたのに監査手続を書いていないか（R4問2）
- [ ] ウの監査証拠が具体的か（文書名・ログ名・期間・件数）（R5問1、R6問2）
- [ ] 問題文の対象を自分で狭めていないか（例: 「運用プロセス」なのに外部サービス部分だけ）（R6問2）
- [ ] ア・イ・ウが同じ事例・同じ項目番号で一貫しているか（R4問1）
- [ ] 監査上の「制約」と、単なる環境変化・課題を混同していないか（R4問1）
- [ ] 一般論で終わっていないか（全年度共通）
- [ ] 字数の下限（イ800字・ウ600字）を超えているか
